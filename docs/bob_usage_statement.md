Our team built ContractGuard around IBM Bob 2.0's Agent mode as the core execution engine, not as a coding assistant bolted onto manual work — the entire detect → repair → verify loop is driven by Bob subagents orchestrated through a Python script (orchestrator.py).

We designed three purpose-built subagents, each with a single responsibility, deliberately kept separate rather than folded into one prompt, since that separation is what let us parallelize and retry independently. The *Impact Agent* runs in Bob's Ask mode and is given the exact old/new schema fragment from a structured diff_report.json (produced by a deterministic OpenAPI diff engine), rather than just a field name — this prevented false positives from unrelated same-named fields. We further split Impact analysis into per-file subagent calls, dispatched up to four at a time via a thread pool, so Bob is genuinely evaluating multiple candidate files in parallel rather than scanning the whole codebase sequentially. We built this as a fail-safe design: if a subagent call errors or returns something Bob couldn't parse, it defaults to "not affected" rather than assuming impact, so a broken subagent call can't silently inflate the report with false positives.

The *Repair Agent* runs in Bob's Agent mode with file-editing permissions and applies the actual code patch — updating generated TypeScript client types, fixing call sites, and adjusting rendering logic. Its prompt is change-type-aware: a renamed field, a changed type, and a removed endpoint each require a structurally different fix (retype vs. remove/guard a call site), and we iterated the prompt specifically to stop it from applying rename-style language to non-rename changes.

The *Verify Agent*, also in Agent mode, runs TypeScript type-checking and the frontend build/test suite and reports pass/fail with logs. We wired a bounded retry loop (max 3 attempts) so that a failed verification feeds the actual compiler error back into the next Repair Agent call — but we capped it deliberately so a stuck loop can't silently burn through our Bobcoin budget or claim a false success. If retries are exhausted, the pipeline reports patch_applied: false honestly rather than faking a pass.

Beyond the three subagents, Bob's document understanding underpinned the whole pipeline: every subagent call is grounded in structured JSON (the diff report, the merged multi-endpoint schema fragments, the verification logs) rather than free-text guessing, which is what let us catch and fix real bugs — including a case where our first real-data run silently discarded two of three genuine breaking-change entries, caught only by inspecting Bob's own subagent output logs.

Each of the three of us set up and used our own hackathon-provisioned Bob account individually (task-session screenshots for each of us are included in evidence/bob-task-sessions/), covering the diff engine, the agent orchestration layer, and the frontend/report viewer respectively — so Bob's usage spans backend, agentic repair logic, and demo integration, not just one workstream.
